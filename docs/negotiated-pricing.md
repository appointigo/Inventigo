# Investigation and implementation notes

Before this change, Product.basePrice entered CartItem.unitPrice. The cart only supported bill-wide discounts. createSale trusted unitPrice and passed it to allocatePricingSnapshots; SaleItem already stored MRP, sellingPrice, allocatedDiscount, taxableAmount, taxAmount, finalLineAmount and effectiveUnitPrice. InvoicePreview read snapshots; returns used a rounded effective unit price. Thus negotiated prices were technically accepted by the service, but cashiers had no item editor, and item discount intent/original selling price was not retained. Inclusive tax was counted twice in effectiveUnitPrice. Legacy rows are normalized using stored sale amounts, never current product prices.

StockEntry.quantity, unique by productId/sizeId/storeId, is checkout's stock source. Product listing used stockEntries.some with sizeId/storeId but no positive-quantity condition. The same where clause serves paginated rows and count. Desktop size choices come from category sizes; mobile previously had no size control. Existing tests include pricing.integration.test.ts, billing.integration.test.ts (outdated database fixtures), saleCompatibility.test.ts and the billing search verification script.

Implementation: fixed item discounts are per unit; percentage is 0–100; direct prices may be above normal price or zero. Original selling price comes from Product.basePrice on the server. Item adjustments precede bill-wide discounts, then tax, then existing whole-rupee invoice round-off. Acquisition cost is only copied into its existing snapshot. New nullable originalUnitPrice/itemDiscountType/itemDiscountValue capture intent. netLineAmount stores the exact after-discount, tax-inclusive line amount before invoice round-off; existing allocatedDiscount stores only bill-wide allocation. Old snapshots and legacy fallback remain unchanged. No historical backfill.
